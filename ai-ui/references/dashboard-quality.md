# Dashboard Quality Protocol — v3.1

## 为什么新增
前版 ARC 在浏览器交互测试通过时，仍存在视觉结果普通、数据密度失衡、次级文字太小的问题。初版 NOVA 同样暴露了两项自动检查漏掉的严重缺陷：所有纵轴标签都变成“0k”；768px 两栏挤压使金额和表格列逐字换行。功能和布局必须分别验收。

## 设计顺序（有约束）
1. 先定义「用户打开页面需要做出的两个决策」与对应数据字段，不要先选择卡片布局。
2. 定义可供核对的数据词典：指标名称、统计期间、单位、正负含义、样本来源、是否合成数据、图表聚合粒度。
3. 指出一个主视觉信息区（通常是核心趋势或异常），必须解释为何它比其他数字重要。容器与空白围绕用户任务，而非四处均衡填充。
4. 写清排版比例（例如 32–40px 主数、16–18px 模块标题、12–14px 正文，灰色文字必须有足够对比度）；表格与辅助数字不应依赖缩小字号换取“精致”。
5. 至少有一种视觉构图差异：跨栏主图、分组 KPI、内容流分区、信息前后关系；不能默认所有区块相同圆角卡片。

## 必须在截图上实测（320、390、768、1024、1440）
- 每个断点实际查看截图；检查大金额是否被挤成两行、表头是否逐字换行、右侧操作是否遮住标题。
- 移动端必须看到每条交易的核心字段（人/金额/状态）。如果改为横向滚动，要给出可见提示并确认信息仍可访问。禁止把关键金额和状态默认藏在视口外。
- 主图必须存在至少三个不同的刻度文字，刻度必须显示正确单位和范围；已显示“上期对照”必须真的有第二条曲线。
- 交互改变期间时，整个页面引用该期间的文案与数据应同步；截图检查默认/非默认状态。
- 用户尚未取得真实数据时，显著标注 Demo。使用随机数不能冒充实时数据；不能伪造用户满意度、增长速度的真实性。
- 空状态、长客户名、七位数收入、缩放 200%、中英文混排都需要至少一轮审查。

## 人工评审（不允许以 ESLint/Playwright 结果代替）
视觉主角是否明确？首屏主任务是否完整？模块密度是否适配工作流？对比度与字号是否达到可读要求？是否有无依据的装饰？是否存在断点失衡？每一项附截图证据和具体修复，不给空泛的“高端/现代”评分。

## 阻断条件
任何明显断点排版破碎、数据语义矛盾、图例与数据不符、关键指标/操作被隐藏、文字可读性不足，均阻断交付。浏览器没有 JS 错误不能覆盖这些缺陷。
